# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A crypto paper-trading app: it connects to live Kraken market data and simulates trading strategies against it, so the user can measure whether active strategies actually beat simply holding (HODLing) before ever risking real money. **Phase 1 (current state) is paper-trading only** — no real orders are ever placed. Phase 2 (live trading via Kraken) is planned but not implemented.

Trading is in **EUR** (`BTC/EUR`, `ETH/EUR`, `SOL/EUR`, `XRP/EUR` — Kraken's native EUR pairs, no FX conversion needed). Internal field/column names still say `_usd` (e.g. `cash_usd`, `starting_balance_usd`) — that's a leftover from before the EUR pivot and was deliberately not renamed to avoid a bigger schema churn; treat those fields as EUR amounts.

The user is a beginner developer; work here proceeds in small, explained, verifiable steps rather than large unreviewed batches.

## Commands

Backend (from `backend/`, Windows/PowerShell):
```
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000 --reload --reload-dir app
```
`--reload-dir app` matters: without it, uvicorn also watches `.venv/`, and any `pip install` inside it triggers a reload storm that can hang the reloader. No linter/formatter is configured for the backend.

`start.ps1` / `stop.ps1` in the repo root launch and stop both servers as processes that outlive the terminal that started them. They exist because the servers were repeatedly being orphaned: over one 194-hour session the bot was down **12.1 hours across 8 outages**, the longest 7.7 hours, every one of them a hole in the trading record and in the order-flow dataset. `stop.ps1` kills the reloader parent *before* the worker and then retries until the port is actually free — a single kill races uvicorn's respawn, which is why a "stopped" backend kept coming back serving stale code.

**Known environment limitation**: inside the Claude Code sandbox, `Get-Process`/`Get-CimInstance` cannot see (or kill) the real uvicorn process — a listening socket shows an `OwningProcess` that resolves to no process at all — and `--reload` does not appear to fire. Restarting the backend to pick up code changes therefore has to be done by the user from an ordinary terminal (`stop.ps1` then `start.ps1`), not from an agent session.

A `backend/tests/` pytest suite covers the pure, high-risk financial logic (`fill_simulator`, `guardrails`, `correlation`, `volatility`, `position_sizing`, `indicators`, the `Grid`/`TrendMomentum` strategies, and a network-free smoke test of the backtest engine with synthetic candles) — run it with `.venv\Scripts\python.exe -m pytest` (`.venv/bin/python -m pytest` on macOS/Linux) from `backend/`. `tests/test_session_loop.py` covers `session/loop.py`'s tick orchestration as well — the regime gate, the 4h filter, sell ownership and handoff margin, sentiment, the stop-loss, session lifecycle, decision-log persistence, and shared-pool sizing — using `tests/conftest.py`'s in-memory database plus scripted strategies injected straight into the instance cache. That injection matters: in auto mode a tick builds every strategy for every symbol, and building one asks Kelly for a size, which runs a live 150-day backtest against Kraken — so pre-seeding the cache (and stubbing `compute_kelly_size_for_strategy`) is what keeps the suite offline and instant rather than hanging. This module went untested for a long time despite being the largest in the project, and **both of the most expensive bugs found so far lived in it or in the backtest engine's mirror of it** — neither was reachable from strategy-level tests, because both were about how the pieces are wired together rather than about any single piece. Still uncovered: the API routes and anything that genuinely hits Kraken. `requirements-dev.txt` adds `pytest` on top of `requirements.txt`.

Frontend (from `frontend/`):
```
npm install
npm run dev       # Vite dev server on http://localhost:5173
npm run build      # tsc -b && vite build
npm run lint       # oxlint
```

Both dev servers must be running simultaneously for the app to work; the backend has no process manager or Docker setup — they're started as two separate local processes. The backend must run on port 8000 and the frontend on port 5173, since CORS in `backend/app/main.py` is hardcoded to allow only `http://localhost:5173`.

The SQLite database (`backend/cripto.db`) is created automatically via `Base.metadata.create_all()` on startup — there is **no migration system** (no Alembic). Adding/changing a column on an existing table requires deleting `cripto.db` and letting it recreate, since `create_all()` only creates missing tables, never alters existing ones. This has happened many times already; it's the normal workflow here, not a special event.

**Windows gotcha**: uvicorn's `--reload` can end up spawning its worker under the system Python instead of the venv Python if a stray process from an earlier run is still bound to port 8000. Before restarting the backend, check for and kill stray `python.exe` processes (`Get-CimInstance Win32_Process -Filter "Name = 'python.exe'"`) rather than assuming the port is free.

## Architecture

### The execution engine seam (paper vs. future live trading)
`app/execution/base.py` defines an `ExecutionEngine` ABC (`place_order`, `get_balance`). `app/execution/paper_executor.py`'s `PaperExecutor` is the only implementation so far, and it deliberately only ever calls Kraken's **public/unauthenticated** ccxt endpoints (`get_ticker_price`) — this is a structural safety property, not just policy: Phase 1 code cannot place a real order even by mistake. A future `LiveKrakenExecutor` would implement the same interface with authenticated ccxt calls; strategies and the session loop only ever talk to the `ExecutionEngine` interface, never to ccxt directly, so swapping executors should not require touching strategy code. `place_order()` returns `Fill | None` — `None` means the order size rounded to zero quantity and was skipped rather than recorded as a no-op trade.

`app/execution/fill_simulator.py` holds the fee/slippage math (`simulate_fill`) as a pure function shared by both `PaperExecutor` (live paper trading) and the backtest engine — this keeps live and backtested fills numerically consistent (0.26% taker fee, 5bps slippage).

### Strategies
`app/strategies/base.py` defines the `Strategy` ABC: `on_tick(ctx: StrategyContext) -> list[TradeSignal]`. Three strategies implement it: `grid.py` (buy-the-dip/sell-the-rise across a fixed price band, with hysteresis via `min_move_pct` so tick-to-tick noise near a level boundary doesn't fire a trade, and band recentering if price wanders out of range for too long), `dca_rebalance.py` (scheduled buys + drift-triggered rebalance sells), `trend_momentum.py` (golden/death cross confirmed by a Bollinger middle-band check, not raw RSI-overbought). `app/strategies/registry.py`'s `STRATEGY_BUILDERS` dict maps a strategy name to a factory function `(symbol, current_price, size_fraction_override=None) -> Strategy` — the single place strategy defaults live; both live sessions and backtests build instances through it. `size_fraction_override` lets the live loop hand the strategy a Kelly-derived size instead of its hand-picked default.

`GridStrategy.last_trade_price` is seeded to the band's own center price (== the price the strategy was built at), not `None` -- otherwise the very *first* trade a fresh instance ever makes has zero `min_move_pct` hysteresis protection (that check only compares a new trade to the *previous* trade, which doesn't exist yet), so a level boundary sitting just a few EUR from the starting price could fire an immediate "dip" buy on pure tick noise seconds after session start, not a real dip -- confirmed live: a fresh session's very first BTC/ETH buys fired within a minute of start on a ~0.01-0.06% wiggle, nowhere near the 0.3% bar every later trade has to clear.

Grid's sell only fires once price clears the position's blended average cost (`StrategyContext.cost_basis`, from `Portfolio.cost_basis` live / the backtest engine's own `avg_cost` tracker) by `min_profit_margin_pct` (default 1.0%, raised from an initial 0.5% once live data showed realized wins clustering at 0.3-0.7% — too close to the ~0.62% round-trip fee+slippage cost, and the displayed gain overstates the true one anyway since `cost_basis` doesn't fold in the buy-side fee, only the sell-side fee is netted out of `realized_pnl`) — not just once price rises one grid level above the last trade. A 150-day backtest showed why this matters: with the old "level rose = sell" rule, grid had a ~50% nominal win rate but average losses 2-4x the size of average wins on all 4 coins (net negative Kelly fraction, i.e. no real edge), because averaging down through several dips and then selling on a modest one-level bounce only has to beat the *last* buy, not the *blended* cost of the whole position still open — so most "wins" were tiny single-level bounces while "losses" were whole averaged-down positions sold underwater. After the fix, the same 150-day backtest shows zero realized losses on all 4 coins (small sample — 6 to 11 trades per coin — so "no losses yet" isn't a guarantee, and the 12%/max-drawdown guardrails remain the only sanctioned way grid ever realizes an actual loss).

`Strategy` also has generic `get_state()` / `load_state(state)` methods (in `base.py`) that snapshot/restore every instance attribute via `vars(self)` (with `set`/`deque` wrapped for JSON-safety) — this is how strategy memory survives a backend restart; see "Strategy state persistence" below. No subclass needs to implement its own serialization.

**`ctx.holdings` is shared, and two strategies each misread it as their own.** The dict lists every coin's quantity for the whole session, so "something is held here" is not the same question as "*I* am invested here" — and neither `holdings` nor `price` (this symbol's only) is enough to work out what share of the portfolio a coin represents. Both gaps produced live bugs, and `StrategyContext` now carries the two missing facts, `position_owner` and `portfolio_value`, set at all six construction sites (two in the live loop, four across the backtest engines — this is exactly the kind of field that silently drifts out of parity otherwise):

- **trend_momentum could not open a position at all.** It read `in_position = ctx.holdings[...] > 0`, so grid's dip-buys made it believe it was already invested. Over one live 8-day session grid held the coins **95.7-100%** of the time and trend_momentum produced **0 buy signals against 12 sells** — it never entered a trade in its own right, it only ever closed other strategies' positions. The entry branch now asks `ctx.position_owner`, while the exit still asks `holdings` (so the regime-flip handoff exit keeps working; the loop decides separately whether that sell is allowed and at what margin). Unknown ownership (`None`) with a real holding stays conservative and does not buy. Measured on the multi-coin backtest with live Kelly sizing, all three windows improved: 30d +9.16%→**+15.89%**, 90d +10.11%→**+19.46%**, 180d +21.22%→**+23.63%** (trend_momentum buys went 0/2/1 → 18/52/18), against max drawdown 7.60→6.88%, 12.59→12.97%, 24.93→26.34%. **This also qualifies the "trend_momentum has no demonstrated edge on SOL/ETH/XRP" claim repeated below**: that conclusion came from a period in which the strategy was structurally unable to enter, so it is evidence about the block, not about the strategy.
- **dca_rebalance measured allocation against the wrong denominator.** It used `held_value / (held_value + cash_usd)`, treating the shared cash pool as the only other asset; with four coins that inflated a real 12.5% ETH weight into a reported **81.8%**, firing rebalance sells on three coins out of four — **424 sell signals against 113 scheduled buys**, all blocked downstream, but all built on a meaningless number (and drowning the decision log: 537 of 555 entries). It now divides by `ctx.portfolio_value`, and treats `0.0` (caller didn't supply one) as "share unknown, don't rebalance" rather than inventing a figure.

`StrategyContext` carries `symbol`, `price`, `cash_usd`, `holdings`, and two sentiment-derived fields, `pause_new_entries` and `size_multiplier` (see "News/sentiment module"). Strategies emit `TradeSignal(symbol, side, size_fraction, reason)`; `size_fraction` means "fraction of current cash" for a buy and "fraction of currently held qty" for a sell (see `fill_simulator.py`).

`"hold"` is a pseudo-strategy handled specially by name in `app/backtest/engine.py` (buy once, hold to the end) — it is **not** in `STRATEGY_BUILDERS` and cannot be selected as a live session strategy; it exists purely as the baseline that active strategies get compared against in backtests. (The live per-session HODL baseline is a different, newer mechanism — see "Portfolio snapshots / HODL baseline".)

### Regime detection and automatic strategy selection
`app/strategies/regime.py`'s `detect_regime(prices, previous_regime)` computes Kaufman's Efficiency Ratio (net price move ÷ total tick-to-tick distance travelled) to classify a coin's recent behavior as `"trending"` or `"ranging"`. It uses a **hysteresis band**, not one shared threshold: switching *into* trending needs the ratio ≥ 0.35 (`ENTER_TREND_THRESHOLD`), switching *out* only needs it to fall < 0.25 (`EXIT_TREND_THRESHOLD`) — this is the same fix pattern as the grid whipsaw bug, applied to prevent the regime (and thus the active strategy) from flapping back and forth on noise. `REGIME_STRATEGY` maps `"trending"` → `trend_momentum`, `"ranging"` → `grid`. `FALLBACK_STRATEGY = "grid"` is used until there are `MIN_HISTORY` (20) ticks of price history.

A session created with `strategy_name = "auto"` (the default — the frontend no longer offers manual strategy selection) uses this per-coin, per-tick: each of the 4 tradable coins can be run by a different strategy depending on its own recent behavior. All three strategies are kept ticking every cycle for every coin (so their internal state — grid levels, moving averages — stays warm even while inactive).

**The regime label no longer decides who may trade.** Buys from any strategy in `REGIME_SELF_GATING_STRATEGIES` (`grid` and `trend_momentum`) execute regardless of which strategy the regime currently favours, because each already refuses its own weak setups — trend_momentum via its confirmed cross / MACD / volume / 4h stack, grid via `min_move_pct` hysteresis and its cost-basis exit discipline. Only `dca_rebalance` is still gated, since it buys on a schedule rather than on a market condition and would otherwise just spend the pool. The gate originally covered grid too, and measurement showed it was doing active harm: over a 29-day window the label read `"trending"` 27-38% of the time, and through those stretches grid's buys were blocked (36 blocked against 13 executed on SOL, 30 against 7 on XRP) while trend_momentum — the strategy the gate handed control to — executed **0-1 buys in the entire period**, because Kelly sizes it at 0.08-0.24 on three of the four coins where it has no proven edge. The bot therefore sat idle for roughly a third of every session: the strategy that would have traded was locked out, the one holding the keys never acted. Removing the gate roughly doubled backtested "auto" returns (+2.7% → +5.3% averaged over both market types and all 4 coins; better in 5 of 8 cases, notably SOL +2.3% → +14.0%), bringing it level with running grid alone (+5.8%) while keeping trend-following upside that grid alone gives up. An earlier, narrower version of this finding is what first exempted trend_momentum: a fully-confirmed BTC golden cross was blocked as `blocked_inactive_strategy` because the cruder regime read (30 raw ticks, ~15 minutes) hadn't caught up, and price kept rising afterward. A **sell** signal executes if it comes from the position's actual owner (whichever strategy's buy created the currently-held quantity, tracked in `session/loop.py`'s in-memory `_position_owners`) or from the currently active strategy — otherwise it's blocked (`blocked_not_position_owner`). This is narrower than "any strategy's sell always goes through": early testing showed trend_momentum treating grid's freshly-bought dip as "its own" position (since it read `ctx.holdings` directly) and closing it out within minutes on its own unrelated exit condition (price below its own moving average, which flips constantly in a ranging market) — a real buy-high/sell-low pattern, not a strategy choosing to exit. The active-strategy carve-out is what still prevents stranding: if the regime flips and the strategy that bought a position loses "active" status, the newly active strategy can still hand off and close it. A regime-flip handoff sell (the active strategy closing a position it didn't open) is further gated: it only executes if it clears the *original* owner's cost basis (`StrategyContext.cost_basis`) by `HANDOFF_MIN_PROFIT_MARGIN_PCT` (1.0%, same reasoning as grid's own `min_profit_margin_pct`) — otherwise it's blocked (`blocked_handoff_below_cost_basis`). A zero-margin version of this check (just "strictly above cost basis") still let a real handoff sell realize a small loss on XRP once the ~0.26% sell fee was applied — clearing cost basis by a hair isn't clearing it by enough to survive real trading costs. Without this, trend_momentum — which has no demonstrated backtested edge on SOL/ETH/XRP, only BTC — was repeatedly closing grid's patient, profit-seeking dip buys at a small loss the moment a regime flip made it "active," undoing exactly the cost-basis discipline grid enforces on its own exits. A strategy closing its *own* position (`strategy_name == owner`) is exempt from this check: cutting a losing trend fast is the point of trend-following, and the 12%/max-drawdown guardrails remain the backstop for a real breakdown regardless of which strategy is managing a position.

Ownership is persisted (`state_store.py`'s `POSITION_OWNER_KEY` sentinel, lazy-loaded into `_position_owners` on first touch per session/symbol after a restart) specifically because this dev workflow restarts the backend constantly (every `--reload`-triggered code edit) — an unpersisted, in-memory-only record would revert to "unknown" on every restart, and unknown ownership falls back to the old permissive behavior (any active-or-owning strategy can sell) precisely to avoid stranding a position whose bookkeeping was genuinely never recorded. Without persistence this permissive fallback would trigger on *every* restart, not just a genuine edge case — which is exactly what let `dca_rebalance` (never active, never an owner, but still ticking and emitting drift-based rebalance sells) sell chunks of a grid-accumulated position hours into a live session, right after an unrelated code change had restarted the backend and wiped `_position_owners`. A session can still be created with a specific fixed strategy name (`"grid"`, `"dca_rebalance"`, `"trend_momentum"`) for that single-strategy behavior across all coins, though the frontend doesn't expose this anymore.

### Multi-coin trading
`app/session/loop.py`'s `TRADABLE_SYMBOLS = ["BTC/EUR", "ETH/EUR", "SOL/EUR", "XRP/EUR"]` — a session doesn't trade one coin, it spreads its shared cash pool across all four; which coin actually reaches the goal doesn't matter. Every tick, `run_tick()` loops over all four symbols, running each coin's strategy/strategies against the *same* `Portfolio.cash_usd` and `Portfolio.holdings` (already a `{asset: qty}` dict, so this needed no schema change). Sizing is self-limiting: `size_fraction` on a buy means "fraction of *current* shared cash," so processing coins sequentially within one tick naturally prevents over-spending even though every coin's strategy independently thinks it can act on the full pool.

### Live tick cadence vs. trend_momentum's candle-based design
Every other strategy reacts to the raw 30s ticker price directly, but `trend_momentum` is fed real hourly OHLCV candles instead, aggregated live from raw ticks by `_update_candle()`/`_candle_buckets` in `session/loop.py` (`CANDLE_INTERVAL_SECONDS = 3600`) — `trend_momentum.on_tick()` is only called once an hour boundary closes, with that candle's close/summed-volume, and is skipped (not even ticked) on every other 30s tick. This exists because `trend_momentum`'s fast/slow SMA periods (5/20) are validated by backtest against daily candles (a 150-day Kelly backtest hits Kraken's ~700-candle cap at finer granularity and falls back to `"1d"`) — feeding the same strategy raw 30s ticks made "5/20 periods" mean 2.5/10 *minutes* instead of days, so it was trading tick noise: real trades round-tripped in 5-10 minutes for a price move smaller than its own ~0.62% round-trip fee+slippage cost, guaranteeing a loss regardless of direction. Hourly candles are a deliberate middle ground (not literally daily) so a live paper-trading session produces its first trend_momentum signal within a day rather than needing weeks of runtime. `grid` and `dca_rebalance` are unaffected — their signals aren't inherently timeframe-sensitive the way a moving-average cross is, so they keep reacting to every raw tick as before.

On top of the hourly cross, a **4-hour trend-agreement filter** gates trend_momentum's buy signal specifically: `_update_4h_candle()`/`_candle_4h_buckets` aggregate the same raw ticks into a coarser 4-hour bucket (`CANDLE_4H_INTERVAL_SECONDS`), and once one closes, `_update_4h_trend()` recomputes a fast(5)/slow(20) SMA over the rolling `_trend_4h_history` (`TREND_4H_HISTORY_LENGTH = 30` candles) and records whether the 4h timeframe itself is in an uptrend (`_trend_4h_uptrend`). A trend_momentum buy is only let through in `run_tick()` if this is `True` — logged as `blocked_4h_downtrend` otherwise, including the "not enough 4h history yet" case (~5 days after session start) rather than defaulting open. This is applied as an external gate in the loop, the same way the regime/ownership/sentiment checks are, not inside `TrendMomentumStrategy` itself, so the strategy's own confirmed-cross logic didn't need to change. The filter exists because a 29-day backtest comparing 1h-only vs. 1h+4h-agreement showed a consistent improvement on **all 4 tradable coins** — higher return, higher win rate, and fewer/lower-quality trades (the 4h view catches exactly the cases where an hourly cross fires against the larger trend, which were disproportionately the losing half of trend_momentum's trades). Like the hourly candle history, `_trend_4h_history` is persisted per (session, symbol) via `state_store.TREND_4H_HISTORY_KEY` so a backend restart doesn't force a fresh ~5-day warmup.

### Order-flow collection (recorded, not traded on)
`app/market_data/flow.py` samples two things plain OHLCV can't express, and `session/loop.py`'s `_record_market_flow()` writes them to the `market_flow_snapshots` table every tick, per symbol:

- **Cumulative volume delta** — `get_volume_delta()` polls `fetch_trades` and sums buy volume minus sell volume since the previous call, deduplicating by trade id (the first call per symbol returns `(0.0, 0)` deliberately: with no previous id there's no way to tell which trades are new, and counting them all would book a large fictitious delta at every backend start). Unlike total volume, which counts both sides of every fill identically, this says *who was crossing the spread*.
- **Open interest** — `get_open_interest()` reads the Kraken **futures** venue (spot has no such concept), cached for 5 minutes since it moves on the scale of hours. `_perp_candidates()` prefers `{COIN}/USD:USD` over `{COIN}/USD:{COIN}`, and that ordering is deliberate and fixed: XRP's coin-margined contract reports ~1,100 open against ~10,300,000 on the USD-margined one, SOL has no coin-margined perp at all, and the two flavours quote open interest in *different units* — so choosing dynamically ("whichever has more") would silently switch units mid-series and corrupt the history. Since the tradable pairs are EUR spot and the perps are USD, this is inherently a cross-market reading.

**Nothing in the trading path reads either value.** They are collected because neither can be backtested from anything Kraken serves retrospectively: OHLCV carries no buy/sell split, the public trade history doesn't reach back far enough to reconstruct months of CVD, and `fetchOpenInterestHistory` is unavailable on both the spot and futures clients. Trading on them today would mean shipping an unmeasured signal — which is exactly what produced three straight failures in one sitting (S/R grid levels, Fibonacci entries, RSI divergence exits: all plausible, all worse than the existing behavior when measured). So the dataset is built first, and hypotheses get tested once there's enough of it. `_record_market_flow()` swallows every exception for the same reason `get_ticker_volume` does: a gap in this dataset is an inconvenience, a tick that didn't run is a missed trade. Read it back via `GET /market/flow` (optional `symbol`, `limit`).

Adding this needed no `cripto.db` reset, unlike a column change — `Base.metadata.create_all()` does create *missing tables*, it just never alters existing ones.

### Why SOL kept looking like the problem coin
SOL repeatedly came out worst in "auto" comparisons, and it was tempting to treat it as simply a bad coin to trade. Measurement says otherwise: over the same 29-day window grid alone returns **+23.2%** on SOL, the best of all four. What is genuinely different about SOL is that it reads `"trending"` **37.6%** of the time (the highest of the four) while Kelly sizes its trend_momentum at **0.08** (the lowest — it has no demonstrated edge there). Under the old regime gate that combination was the worst possible: SOL was locked out of grid more often than any other coin, and handed each time to the one strategy sized almost out of existence. SOL wasn't a bad coin, it was the coin the gate hurt most — which is why removing the gate moved it further than any other (+2.3% → +14.0%).

### News/sentiment module
`app/news/fetcher.py` pulls recent headlines from CoinDesk and Cointelegraph RSS feeds (no API key needed). `app/news/sentiment.py` scores each headline -1..1 with a small, readable keyword lexicon (`hack`, `ban`, `crash`, ... negative; `rally`, `etf approval`, `adoption`, ... positive). `app/news/reactor.py`'s `get_sentiment_state()` averages the scores across all fetched headlines and derives a `SentimentState` (`avg_sentiment`, `pause_new_entries`, `size_multiplier`) using its own thresholds (`PAUSE_THRESHOLD = -0.3`, `SEVERE_THRESHOLD = -0.6`); it's cached for 5 minutes (`CACHE_TTL`) so a 30s trading tick doesn't hit the RSS feeds every cycle. `session/loop.py` applies this centrally, not inside each strategy: a **buy** signal is dropped entirely if `pause_new_entries`, or shrunk by `size_multiplier` otherwise; a **sell** signal is never blocked by sentiment — bad news should never prevent getting out of a position.

### Correlation-based position sizing
`app/risk/correlation.py`'s `get_correlation_matrix(symbols)` fetches 90 days of historical OHLCV for each tradable symbol (via `backtest/data_loader.py`, so it inherits the same timeframe/lookback-cap behavior) and computes a pairwise Pearson correlation matrix of daily returns; it's cached for 1 hour (`CACHE_TTL`) since this means 4 historical-data fetches and a 30s tick shouldn't pay that cost every cycle. `correlation_size_multiplier(symbol, holdings, prices, correlation_matrix)` shrinks a **buy** signal's size the more the target coin is correlated (value-weighted) with what's already held — above `HIGH_CORRELATION_THRESHOLD` (0.7) it scales linearly down to `MIN_SIZE_MULTIPLIER` (0.3) at perfect correlation, never blocking the buy outright the way sentiment's `pause_new_entries` can. `session/loop.py` fetches all 4 symbols' prices upfront (not lazily per-symbol as the loop progresses) specifically so this multiplier always has every held asset's current price available, and re-reads `portfolio.holdings` on every signal (not once per tick) so an earlier buy/sell within the same tick already counts toward sizing a later one. **Not yet covered**: this sizing only runs in the live loop — `app/backtest/engine.py` doesn't apply it, so a strategy's backtested Kelly fraction (see below) doesn't reflect the extra shrinkage it will actually get live.

### Risk guardrails (independent of any strategy)
`app/risk/guardrails.py`'s `check_drawdown_limit(current_value, past_values, max_drawdown_pct)` is a small, strategy-agnostic gatekeeper: every tick, `run_tick()` computes the session's total portfolio value (cash + all coin holdings at current prices), compares it to the highest value the session has ever reached (from its own `PortfolioSnapshot` history, via a SQL `MAX()` — it used to load every snapshot row to take a maximum in Python, which after 8 days was 22 349 rows / ~29ms on every 30-second tick and growing without bound, the same mistake the snapshots endpoint had), and if the drawdown from that peak exceeds `TradingSession.max_drawdown_pct` (default 20%, set at session creation), the session's status flips to `"risk_stopped"` — regardless of what the active strategy thinks it's doing. This is deliberately separate from strategy logic (a "dumb," strict layer, not a smart one) and separate from the upside `target_balance` check. `POST /session/stop-all` is a kill switch that immediately stops every session in play (`"running"` or `"target_reached"`), independent of any one session's own logic.

The same module's `check_position_stop_loss(current_price, avg_cost)` is a second, narrower guardrail: it compares one held *position* (not the whole portfolio) against its own weighted-average entry price — `Portfolio.cost_basis` (a `{asset: avg_price}` JSON dict, mirroring `holdings`), updated by `PaperExecutor.place_order()` using the same weighted-average formula the backtest engine uses for its own win/loss accounting. If a position has fallen `STOP_LOSS_PCT` (12%, a module constant, not yet session-configurable) below its entry, `run_tick()` force-sells it *before* that symbol's strategies even tick this cycle — a strategy's own exit condition (death cross, band break, a grid level recovering) can lag well behind a fast drop, so this doesn't wait for one. Because the liquidation happens outside any strategy's own `on_tick()`, each `Strategy` has an `on_external_sell()` hook (no-op by default) that `run_tick()` calls on every strategy instance ticking that symbol right after a forced sell, so position-tracking state doesn't go stale — `GridStrategy` clears `owned_levels` (otherwise it would refuse to re-buy a level it no longer actually holds) and `TrendMomentumStrategy` resets `in_position` (otherwise it would refuse a legitimate new buy until a death cross happened to occur too). `dca_rebalance` needs no override since it re-derives its allocation from `ctx.holdings` fresh every tick rather than caching an in/out flag.

**`on_external_sell()` fires on ordinary sells too, not just the stop-loss** — it originally didn't, and that was a real bug caught live on XRP. A handoff sell closed grid's entire position on a regime flip, nothing told grid, and grid went on listing levels 2/3/4 as owned against a position it no longer held. Because grid only buys a step *down* into a level it doesn't already hold, those phantom levels silently locked it out of the 1.19-1.23 EUR range it was actually flat in — it wasn't refusing to trade, it believed it had already bought there. Two cases now notify: the sell emptied the position (nobody holds anything, so no level can still be owned — every strategy is told, the seller included, since grid's own sell frees a *fraction of the holding* rather than one specific level and can likewise be left listing levels against an empty position), or it was a handoff sell by a strategy that didn't open the position (the real owner's per-level bookkeeping is now unreliable; the seller keeps its own state, which is about its own logic). Clearing is the safe direction to be wrong here: a strategy that wrongly forgets a level becomes willing to re-buy it, while one that wrongly remembers a level stops trading a price range with no visible symptom — and grid's cost-basis exit rule still prevents selling at a loss either way.

### Strategy state persistence
`app/session/state_store.py`'s `save_state()` / `load_state()` read/write the `StrategyState` table, keyed by `(session_id, symbol, strategy_name)`. `session/loop.py` calls `strategy.get_state()` and persists it after every tick for every strategy touched (not just the active one), and on a cache-miss (first access after a process restart) calls `strategy.load_state()` to restore it before the strategy does anything — this is what lets a grid's exact band boundaries, owned levels, and hysteresis memory (and a DCA strategy's tick counter, and trend/momentum's moving-average history) survive a backend restart instead of resetting. The special `strategy_name` value `state_store.REGIME_HISTORY_KEY` (`"_regime_history"`) is reused for the same purpose to persist each coin's recent price history and last-known regime (used to seed the hysteresis check after a restart), even though it isn't a real strategy.

Note this doesn't make strategy state durable against *anything* — restarting mid-tick, concurrent writers, etc. aren't guarded against. It solves the specific, repeatedly-hit problem of "the dev server reloaded and the bot forgot everything."

### Live paper-trading loop
`app/session/loop.py`'s `run_tick(db, session_id)` is the per-session tick: for each of the 4 tradable symbols, fetch price → (in auto mode) update regime history and pick the active strategy → build `StrategyContext` (including the current sentiment state) → tick every candidate strategy for that coin → route buy signals from the active strategy (and sell signals from any strategy) through `PaperExecutor` → after all coins, record a `PortfolioSnapshot` and run the target/drawdown checks. Strategy instances are kept in an in-memory dict (`_strategy_instances`, keyed by `(session_id, symbol, strategy_name)`) for fast access within one process's lifetime; see "Strategy state persistence" for how this survives a restart.

`app/scheduler.py` runs an APScheduler job every 30s that calls `run_tick()` for every `TradingSession` with `status == "running"` — this is what makes paper trading happen automatically without the frontend polling triggering it. There's also a manual `POST /session/{id}/tick` endpoint for on-demand testing without waiting for the scheduler. If a tick takes longer than 30s (e.g. many running sessions × 4 coins × Kraken API latency), APScheduler logs a "maximum number of running instances reached" warning and skips that cycle rather than overlapping — not an error.

Every signal any candidate strategy produces this tick — not just the ones that execute — is recorded to the `decision_log` table via `_log_decision()` (not committed there; `run_tick` commits once at the end, so a decision and the trade it describes land together or not at all). This used to be an in-memory `deque` that a restart erased — measured over one 194-hour session that happened 8 times, so the record of *why the bot didn't trade* was routinely gone before anyone looked. Each entry carries an `outcome` of `executed`, `blocked_inactive_strategy`, `blocked_4h_downtrend` (a trend_momentum buy where the 4-hour trend filter disagrees — see "Live tick cadence vs. trend_momentum's candle-based design"), `blocked_not_position_owner` (a sell from a strategy that neither opened the position nor is currently active — see "Multi-coin trading"), `blocked_sentiment_pause`, `zero_after_sizing` (size shrunk to nothing by sentiment/correlation/concentration sizing), or `stop_loss_triggered`. `get_decision_log(db, session_id)` / `GET /session/{id}/decisions` exposes it, and `GET /session/{id}/strategy-performance` answers the related question the trade table can't — *which strategy actually made or lost money*. That view attributes each sell's realized P&L from the trade's `reason` prefix (`"grid: ..."`, `"trend_momentum: ..."`, `"risk: stop-loss ..."`) rather than from a dedicated column, so it works on every trade already recorded instead of only on ones made after it existed. Credit goes to whichever strategy *closed* the position, which is what makes regime handoffs visible: on one live session trend_momentum had 0 buys but 3 sells worth +17.02 EUR — all of them handoff exits of grid's positions, against grid's own 7 exits totalling +4.05 EUR. This is what lets the frontend show *why* a strategy that looks "active" in the regime table still isn't trading (e.g. `trend_momentum` firing a golden-cross buy signal on a coin currently in `"ranging"` regime gets logged as `blocked_inactive_strategy`, not silently dropped) — the trade table alone only ever shows what *did* happen.

### Goal-based sessions
`TradingSession.target_balance` (optional) and `.max_drawdown_pct` (optional, default 20%) drive two independent auto-stop checks each tick. `status` is one of `"running"`, `"stopped"` (user-initiated, via `/stop` or `/stop-all`), `"target_reached"` (upside goal hit — the scheduler excludes non-`"running"` sessions, so it naturally pauses here), or `"risk_stopped"` (downside guardrail tripped). From `"target_reached"`, `POST /session/{id}/target` sets a new target and resumes the session to `"running"`; `"risk_stopped"` currently has no auto-resume path (closing it is the only action) — restarting after a risk-driven stop is meant to require a conscious decision, not a quick undo.

### Portfolio snapshots / HODL baseline
`TradingSession.starting_prices` (a `{symbol: price}` JSON dict, captured once at session creation) lets the app compute, at any later point, what an even split of the starting balance would be worth today if it had been bought once across all 4 coins and never touched again — the "HODL" comparison baseline, without needing to fetch historical OHLCV. Every tick, `run_tick()` inserts a `PortfolioSnapshot` row with both the session's actual `total_value_eur` and this `hodl_value_eur`. `GET /session/{id}/snapshots` returns the full time series; the frontend's `EquityChart.tsx` renders it as a hand-rolled inline-SVG line chart (bot vs. HODL, no charting library dependency).

### Backtesting
`app/backtest/engine.py`'s `run_backtest()` replays a strategy candle-by-candle over historical OHLCV using the same `simulate_fill()` as live trading, tracking an average cost basis to classify each closing trade as a win or loss. `app/backtest/data_loader.py` fetches historical OHLCV from Kraken via ccxt — **important gotcha**: Kraken's public OHLC endpoint only ever returns the most recent ~700 candles for a given timeframe, regardless of how far back `since` points, so requesting more history than that at a fine timeframe silently truncates to a recent window instead of erroring. `pick_timeframe()` picks a coarser timeframe (1h → 4h → 1d → 1w) as the requested day range grows, to stay under that cap; for an explicit date-range backtest (`fetch_ohlcv_between`), the timeframe choice is based on how far the *start* date is from *now*, not the window length, since Kraken's cap counts back from the present.

`app/backtest/validation.py` does a simple train/test split (not full walk-forward optimization) to check whether a strategy's behavior is consistent across different sub-periods, since strategies use fixed hand-picked parameters rather than parameters fit to the data. `run_backtest("auto", symbol, candles)` (via the private `_run_auto()`) replays the same regime-based per-coin strategy switching as a live auto session, but — like every other mode above it — only for **one symbol at a time**; it has no notion of a shared cash pool or of what other coins the same session would be holding. `_run_auto()` now also mirrors the live loop's position-ownership + `HANDOFF_MIN_PROFIT_MARGIN_PCT` handoff gating (see "Regime detection and automatic strategy selection") — it didn't originally, which meant this specific backtest mode was silently testing an older, more permissive "any strategy's sell always goes through" rule that live auto sessions haven't actually used since that gating was added. This was found by diagnosing why a 29-day BTC "auto" backtest returned only +1.4% while price itself rose +22.6%: trend_momentum was whipsawing out grid's dip-buys within hours of every regime flip, at a negligible or negative margin, something the live gating would have blocked. Fixing it roughly doubled-to-quadrupled the backtested "auto" return on all 4 coins (BTC +1.4%→+3.0%, ETH -0.5%→+3.2%, SOL +1.4%→+5.4%, XRP +0.3%→+4.0%) — still well behind HODL's 22-40% in that specific strong-uptrend window, but that remaining gap is the expected, structural cost of an active strategy taking profits along the way (protecting against a reversal that didn't happen in this window) rather than staying fully exposed like HODL, not a further bug. `HANDOFF_MIN_PROFIT_MARGIN_PCT` itself was moved from `session/loop.py` to `app/constants.py` (alongside `TRADABLE_SYMBOLS`, for the same reason: so the backtest engine can import it without a circular dependency) so both places share one definition. `run_multi_coin_backtest()` applies the same rules (it tracks `position_owners` per asset), and `_run_auto()` now also simulates the 12% position stop-loss it was missing. Both engines and the live loop share `REGIME_SELF_GATING_STRATEGIES` and `HANDOFF_MIN_PROFIT_MARGIN_PCT` from `app/constants.py` rather than each defining their own — every time those drifted apart, the backtest silently reported a different bot than the one that runs.

**Position sizing was a second, larger backtest/live mismatch of the same kind.** Every backtest entry point takes an optional `size_fraction_override` (a float, or a per-strategy dict — see `_resolve_size_override()`), passed through to `STRATEGY_BUILDERS`. It defaults to `None`, meaning each strategy's own hand-picked default — which is what Kelly sizing itself must use, since `risk/position_sizing.py` imports this module and computing Kelly here would both recurse and be a circular import. But a *live* session never uses those defaults: it passes each strategy the Kelly-derived size instead, and live grid sits at the 0.8 `max_fraction` cap against its own 0.1 default — an **8x gap**, which is why "auto" backtests looked barely invested (20-48% average exposure) while the real bot runs at ~99%. `risk/position_sizing.py`'s `live_size_overrides(symbol)` returns the live-equivalent dict for this parameter; note its own caveat that Kelly is computed from the most recent ~150 days, so applying it to an older backtest window is a mild look-ahead. Re-running the same 29-day comparison with live sizing moved BTC's "auto" from +2.8% to **+21.9%** (versus HODL's +21.8% — essentially matching it), but moved XRP from +4.0% to **-2.9%** and SOL from +5.0% to +2.9%: bigger size is emphatically **not** a free improvement, it amplifies whatever the timing already was. That result is what settled an open question about whether the live bot should size up further ("always go all in") — it shouldn't, and it already effectively is at ~99% exposure. On the sideways windows, live sizing beats HODL on 3 of 4 coins, which is the regime the strategy is actually designed for.

Two known remaining gaps in `_run_auto()` specifically: it does **not** simulate the 12% position-level stop-loss (only `run_multi_coin_backtest()` does), so a backtested drawdown past that (e.g. XRP hitting 13.2% above) would have been cut short live; and being single-symbol it has no shared cash pool, so it can't show coins competing for the same capital.

`run_multi_coin_backtest()`, further down the same file, is the one that does: it replays all 4 tradable coins in lockstep against one shared cash pool, applying the same correlation-based (`correlation_size_multiplier`) and concentration-cap (`concentration_size_multiplier`) buy sizing and the same position-level stop-loss (`check_position_stop_loss`) a live session actually applies — none of which the single-symbol `run_backtest()` can model, since correlation/concentration sizing is only meaningful when other coins' holdings exist to compare against. `_align_candles()` intersects every symbol's candle timestamps first, so "step N" means the same moment across all 4 coins even if their histories differ slightly in length or start. Its correlation matrix is a **one-time snapshot** computed from the backtest window's own returns (via `app/risk/correlation.py`'s `compute_correlation_matrix_from_returns()`, factored out of the live-fetch path so both share the same math) — not rolled forward candle-by-candle the way the live 1-hour cache effectively does over time; this is the same kind of acknowledged simplification as the train/test split above. News sentiment has no equivalent here at all — there's no historical headline archive to replay, so a backtest (multi-coin or not) can never reproduce the live loop's sentiment-driven buy throttling. Exposed via `POST /backtest/multi-coin/{strategy_mode}` (`strategy_mode` is `"auto"` or a fixed strategy name), returning both the bot's and an even-split HODL baseline's total return so the two are directly comparable, the way the live per-session snapshots are. `TRADABLE_SYMBOLS` itself now lives in `app/constants.py` rather than `session/loop.py`, purely so this module and the live loop can both import it without an import cycle (`session/loop.py` already depends on `backtest/engine.py` indirectly through `risk/position_sizing.py`'s Kelly sizing).

### Risk/analysis module
`app/risk/profiles.py` defines risk bands (low/medium/high → max drawdown % caps) used for *backtest-based recommendation*, separate from the live per-session `max_drawdown_pct` guardrail described above. `app/risk/recommender.py` pulls each strategy's latest `StrategyPerformanceRecord` (including `"hold"`) for a symbol, filters to those within the chosen risk band's drawdown cap, and recommends the top return among eligible candidates — with a rationale and the full candidate list so the UI can show why. `app/risk/position_sizing.py`'s `kelly_fraction()` computes a half-Kelly, capped position size from a backtest's win/loss trade P&Ls (returns `max_fraction` rather than 0 when there are wins but no losses yet). `max_fraction` defaults to **0.8** (raised from an initial 0.5) after a trend_momentum position-size sweep backtest (0.2 through 1.0, on the 4h-filtered variant above) showed every tradable coin's max drawdown staying under the 12% position stop-loss up to roughly 0.8 — still paper trading, so the accepted risk ceiling is deliberately higher than a live-money Kelly gate would normally allow; ETH/XRP already exceed the 12% stop-loss above ~0.6-0.8, so the backtested return at the very top of the range (close to 1.0) is optimistic, since a real position-level stop-loss would have exited before the full backtested drawdown played out. `compute_kelly_size_for_strategy()` floors this at `MIN_LIVE_KELLY_FRACTION` (0.08) before handing it to live sizing — a strategy whose backtest showed a negative edge otherwise gets a raw Kelly fraction of exactly 0.0, which meant it could never place a real live order at all; the floor deliberately accepts more live risk than a strict Kelly gate would, purely so an unproven/losing-edge strategy still trades small instead of being fully shut out. This floor only matters for a strategy that's actually losing money in its own backtest — once grid's own sell logic was fixed (see the `cost_basis`/`min_profit_margin_pct` note above) its real backtested Kelly fraction jumped to the `max_fraction` cap on all 4 coins, comfortably clearing the floor. `kelly_fraction()` itself (used by the `/backtest` Kelly endpoint) is untouched by the floor, so backtest analytics still show the honest, unfloored number. `compute_kelly_size_for_strategy()` is wired into live sizing: `session/loop.py` calls it when first building a strategy instance and passes the result as `size_fraction_override`, falling back to the strategy's own default if the Kraken data call fails (e.g. rate limited) rather than failing the tick. `app/risk/monte_carlo.py`'s `run_monte_carlo()` bootstrap-resamples a backtest's daily returns to estimate VaR/CVaR and loss probabilities.

### API surface (all routers mounted in `app/main.py`)
- `GET /market/ticker/{symbol:path}` — live price (note the `:path` converter, needed because symbols like `BTC/EUR` contain a `/`)
- `GET /market/daily-range/{symbol:path}` — today's (UTC calendar day) high/low; `GET /market/overview` — price, today's high/low and the 24h change for **all four** tradable coins in one response, since the dashboard shows them side by side and refreshes every 5s. `kraken_client.get_market_overview()` caches each symbol for 30s: uncached this would be ~48 Kraken calls a minute competing with the trading tick for the same rate limit. One coin failing returns empty fields for that coin rather than failing the whole response.
- `/session` (`routes_session.py`) — create/stop/get a session, `GET /active` (most recent running/target-reached session, for the frontend to reconnect to on page load — see below), `POST /stop-all` (kill switch), `POST /{id}/target` (set new target, resume), place a manual order, list trades (each sell's `realized_pnl`/`realized_pnl_pct` is reconstructed on the fly by replaying the session's trade history with the same weighted-average cost-basis formula `PaperExecutor` uses live — not stored on the `Trade` row, so adding this needed no schema change/`cripto.db` reset), list snapshots, get per-coin regime state, `GET /{id}/decisions` (the decision log — see "Live paper-trading loop"), `GET /{id}/chart-data` (per-coin price/volume/RSI/MACD series for the `CoinChart` component — see "Frontend"), manual tick
- `/strategies` (`routes_strategies.py`) — lists `STRATEGY_BUILDERS` keys (does not include `"hold"` or `"auto"`)
- `/backtest` (`routes_backtest.py`) — run a backtest, train/test validate, Kelly position-size, Monte Carlo, list stored performance records; `POST /backtest/multi-coin/{strategy_mode}` runs the shared-cash-pool, all-4-coins version (see "Backtesting")
- `/recommendation` (`routes_risk.py`) — backtest-based strategy recommendation for a risk band
- `/news` (`routes_news.py`) — recent scored headlines + average sentiment; `/news/sentiment` — just the current `SentimentState`

### Frontend
Single-page app (`frontend/src/App.tsx`, no router/multiple pages yet). On mount, it calls `GET /session/active` to reconnect to whatever session is still running on the backend — the frontend holds no session id in storage, so without this, refreshing the page during a running session would silently lose track of it (the backend keeps running regardless; only the UI's view of it was lost). No manual strategy picker anymore — starting a session always uses `"auto"` mode; the pre-session card still shows the risk-band recommendation (informational) plus starting balance, optional target, and the drawdown limit.

**Design language.** The UI was rebuilt from a warm-paper, card-based design (light `#faf6ee` ground, white cards, Bricolage Grotesque / Work Sans / JetBrains Mono, one sage and one clay accent — all tokens in `index.css`). It replaced a dark neon/sci-fi theme that stacked every panel in a single 960px column; the two complaints that drove the redesign were the style itself and the fact that nothing could be seen side by side. Two rules carry the whole layout and should survive future edits: **every card opens with a one-sentence plain-Hungarian explanation** (`.card-note`) before showing any number, and **the "is the bot beating HODL?" verdict is the largest thing on the page**, stated as a sentence with the euro difference inline rather than buried in a paragraph. Tables are CSS grids (`.trade-row`, `.strategy-row`, `.holding-row`, `.flow-row`, `.decision-row`), not `<table>` elements, so one cell can hold a sentence, another a stacked pair of numbers, and another a bar — and so they can collapse to a stacked single column under 1040px, where the header row is hidden outright rather than squeezed. Icons are inline SVG, never emoji.

Each coin card ends with **what that coin is waiting for**, as two concrete prices from `GET /{id}/plan` (`loop.get_strategy_plan`): the price a grid buy fires below, and the price a sell fires above. This exists because the card's daily-range bar kept reading as "price is at the bottom, why isn't it buying?" — and it never was that question. Grid doesn't buy low prices, it buys a step *down* into a level it doesn't already hold, and it won't sell until price clears the position's blended cost basis by `min_profit_margin_pct`. Both are exact numbers. One subtlety the endpoint has to respect: while grid holds a level underwater it keeps `last_level` pinned there (see `grid.py`'s hold branch, which returns before updating it), so the next buy level can be well below the one immediately underneath — on a live ETH position holding levels 2/4/5/7 at a 2 203,49 EUR blended cost, the real next buy was 2 118,29 (level 1), not the empty level 3 the price was sitting in. `trend_momentum` coins report no thresholds rather than inventing one, since a confirmed moving-average cross doesn't reduce to a single price.

A running session shows, in order: the **verdict card** (headline sentence, bot vs. HODL figures, `EquityChart`, and a six-cell meter strip — runtime, trade count, closed positions and win rate, total fees, drawdown against the session's own limit, target progress), the target-reached/risk-stopped banners, a **per-coin card** for each tradable coin (`CoinCard.tsx`: `Sparkline` of the recent price with buy/sell markers, 24h change, today's high/low with the current price's position inside it, regime + active-strategy tags, open position value, average entry price and unrealized P&L), **"Mit csinált a bot"** (recent trades, each as a sentence with the strategy's raw `reason` underneath — the reason is never rewritten, only led with a plain-language line), **"Amit nem csinált meg"** (blocked signals ranked by reason with counts, plus the most recent few), **"Melyik stratégia hozott pénzt"** (from `GET /{id}/strategy-performance`), **"Miben áll a pénz"** (cash, allocation bar, per-coin quantity/value/weight), **"Vevői és eladói nyomás"** (the collected CVD/open-interest data, explicitly labelled as not traded on), the news/sentiment card, the full **decision log** with its executed-only filter, and **"Részletes grafikonok"** (one `CoinChart.tsx` per coin — price/volume/RSI/MACD from `GET /{id}/chart-data`).

`CoinChart`'s price line is overlaid with small buy/sell triangle markers (green up / red down) at each of that coin's trades, positioned by finding the chart sample whose timestamp is closest to the trade's; only trades that fall inside the chart's own visible window get a marker. That window (`session/loop.py`'s `CHART_HISTORY_LENGTH`, 240 ticks / ~2 hours) is deliberately decoupled from `REGIME_HISTORY_LENGTH` (30 ticks), which is what the strategies themselves actually see for regime detection — the chart exists for a human to look at and can show more history without changing any trading behavior.

A global "Mindent leállít" button (kill switch, calls `stop-all`) sits in the header regardless of whether a session is loaded. The session panel polls every 5s while `status === "running"`; news/sentiment polls every 60s; the ticker overview and order-flow history poll every 30s on their own timer, because they are market data rather than session data and keep accumulating whether or not a session is running. `frontend/src/api.ts` is a thin typed fetch wrapper around the backend — no other HTTP client library is used. `EquityChart.tsx` and `Sparkline.tsx` are hand-rolled inline-SVG chart components (no charting library). Shared bits live in `format.ts` (Hungarian number formatting — space thousands separator, comma decimal; `priceDigits()` gives XRP four decimals and the rest two) and `labels.ts` (regime/strategy/outcome label maps, previously duplicated inside `App.tsx`).
